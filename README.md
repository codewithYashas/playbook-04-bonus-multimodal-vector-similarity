# ByteEats Vector Similarity

Food-prep videos and reference dish photos in one LanceDB database: the files, their frames, their metadata and their ResNet-18 vectors stored together, then searched, quality-checked and explored from a Streamlit app.

This is a LanceDB port of the **Chapter 4 bonus playbook** of *Data Engineering for Multimodal AI* (O'Reilly, 2026), [playbook-04-bonus-multimodal-vector-similarity](https://github.com/Data-Engineering-for-Multimodal-AI/playbook-04-bonus-multimodal-vector-similarity). The original wrote each embedding to a `.npy` file with a JSON sidecar, loaded them into an in-memory FAISS index at API startup, and showed them in a Dash dashboard behind a FastAPI server. See [Ported from the original](#ported-from-the-original).

## The problem and the app

A ghost kitchen films every bowl it prepares. Operations wants to know two things: which prep videos look like which menu dish, and whether a given video actually shows the dish it should. That's similarity search over video and image embeddings, plus a per-frame check against a reference photo. Here the media, the per-frame vectors and the per-video vectors all live in LanceDB tables, so each question is one query.

The page has three tabs, a details dialog, and a Debug toggle for presenters.

- **Search.** Pick a query (a reference dish, a video, or an uploaded photo) and what to find (videos, reference dishes, or individual video frames). Results come back as a gallery with cosine similarity. **Details →** opens the dialog.
- **Explore.** The stored vectors (39 videos and dishes, or 768 frames), projected to 2-D with UMAP and clustered with K-Means or HDBSCAN in the full 512-d space. Each cluster is named after the reference dish nearest its centroid, found with a LanceDB search that uses the centroid as the query. Click a point to open it. Outliers are listed below.
- **Check.** The book's quality check. Pick a dish, a video and a pass threshold. The check is one vector search: the dish photo's vector against that video's 24 stored frames, prefiltered by `video_id`. The page shows the best frame next to the reference, the similarity of every frame over the clip, and PASSED or FAILED. Below that, a single search over all 768 frames ranks every video against the dish.
- **Details dialog.** The video (playing inline from the bytes in the table) or the photo, its metadata, a strip of its sampled frames, its nearest neighbours as ranked bars and thumbnails, and where it sits on the map of all 39. Clicking a neighbour or a point moves the dialog to it.
- **Debug** (sidebar, off by default). Each result set gets a **LanceDB query** expander showing the exact query-builder chain that ran. Under the tabs, **Raw table** shows rows of `media` or `frames` with vectors and blobs summarised, **Table stats** shows schemas, indexes and versions, and **All queries this run** lists every query in order.

The page only reads. The tables and indexes come from the numbered scripts.

## Quick start

You need [uv](https://docs.astral.sh/uv/getting-started/installation/). uv installs Python 3.12 or newer if you don't have it.

1. Install:
   ```bash
   uv sync
   ```
2. Embed the media into LanceDB and build the indexes (about 30 seconds on an Apple-silicon laptop CPU; the first run downloads the 45 MB ResNet-18 weights):
   ```bash
   make data    # scripts/01_embed_media.py, then scripts/02_create_indexes.py
   ```
3. Run the app at http://localhost:8041 (chapter 04, bonus playbook; set in `.streamlit/config.toml`):
   ```bash
   make run     # uv run streamlit run app/app.py
   ```
4. Optional: compare index types on the frames table:
   ```bash
   make compare # scripts/03_compare_indexes.py
   ```

`make smoke` runs the pipeline on 3 videos and checks the guide's numbers and the app, in about a minute. `make check` runs ruff.

## Schema

Two tables in `byteeats.lancedb/`, with explicit Arrow schemas in `scripts/common.py`.

`media`: one row per video and per reference image (39 rows).

| Column | Type | Holds |
|---|---|---|
| `media_id` | `string` | `download (15)`, `Tuna_Lover` |
| `media_type` | `string` | `video` or `image` |
| `filename` | `string` | The source file name |
| `dish` | `string` | The dish a reference image shows (`Tuna Lover`); null for videos |
| `width`, `height` | `int32` | Pixels |
| `duration_s`, `fps`, `frame_count` | `float32`, `float32`, `int32` | Videos only |
| `frames_embedded` | `int32` | How many frames the video vector averages (24) |
| `file_size_bytes` | `int64` | |
| `media` | `large_binary` | The MP4 or JPEG itself |
| `thumbnail` | `binary` | A 320-px JPEG (the middle frame, for videos) |
| `embedding` | `fixed_size_list<float32>[512]` | ResNet-18, L2-normalised; for a video, the normalised mean of its frames' features |
| `model`, `embedded_at` | `string`, `timestamp` | Provenance |

`frames`: every 5th frame of every video (24 per clip, 768 rows).

| Column | Type | Holds |
|---|---|---|
| `frame_id` | `string` | `download (15)#0035` |
| `video_id` | `string` | The `media_id` of its video |
| `frame_index`, `timestamp_s` | `int32`, `float32` | Where in the clip |
| `thumbnail` | `binary` | A 224-px JPEG |
| `embedding` | `fixed_size_list<float32>[512]` | ResNet-18 of the frame, L2-normalised |

| Index | On | Why |
|---|---|---|
| `embedding_idx` | `frames.embedding` | IVF_HNSW_SQ, cosine, 3 partitions: frame search and the quality check |
| `video_id_idx` | `frames.video_id` | BTree: the quality check's prefilter and the dialog's frame strip |
| `media_type_idx` | `media.media_type` | Bitmap: video-only or dish-only searches |
| `media_id_idx` | `media.media_id` | BTree: lookups by id |

`media` has no vector index on purpose. At 39 rows an exact scan is the fastest and most accurate search, and the page says so.

## LanceDB features demonstrated

- **Vectors stored with the data.** The MP4s, JPEGs, thumbnails, metadata and embeddings sit in the same rows. A search returns a thumbnail and a similarity in one round trip, and nothing has to be kept in sync with a folder of `.npy` files.
- **Two granularities, one database.** Per-video vectors in `media` answer "which videos look like this dish", and per-frame vectors in `frames` answer "which moment of this video matches".
- **Prefiltered vector search.** The quality check is `frames.search(dish_vector).where("video_id = 'download (15)'", prefilter=True)`, served by a BTree index.
- **Index choice, measured.** `03_compare_indexes.py` builds IVF_FLAT, IVF_PQ, IVF_SQ and IVF_HNSW_SQ in turn on a copy of `frames` and reports recall@10 against an exact scan. The sidebar's **Exact frame search** toggle (`bypass_vector_index()`), **nprobes** and **refine_factor** tune the same searches live.
- **Search with a computed vector.** Cluster names come from searching `media` with a cluster centroid as the query vector.
- **Remote-safe reads.** Every read is a query with an explicit limit (`table.search().where(...).select(...).limit(n)`), which also works against LanceDB Cloud and Enterprise tables.
- **The query, as it ran.** The Debug panels print each query from the same step list the page executes.

## Connection profiles

The page and the scripts read `BYTEEATS_URI` (default `byteeats.lancedb` in the repository root). The sidebar's **LanceDB connection** panel can change it.

Profiles live in `~/.lancedb/profiles.toml`, shared with the other fe-demos. This demo reads a profile's `byteeats_uri`, plus the shared `api_key`, `region` and `host_override`:

```toml
[my-cluster]
api_key = "ldb_..."
region = "us-east-1"
host_override = "https://your-endpoint.example.com"   # optional
byteeats_uri = "db://byteeats"
```

`LANCEDB_PROFILE` names the profile to start on; a blank value means none. With no `[my-cluster]` profile, everything runs locally. The scripts take `--uri` and `--profile`, so `uv run python scripts/01_embed_media.py --profile my-cluster` writes the tables to the cloud database directly (in requests of at most 24 MiB, since the videos travel inline). API keys never become widget values in the page.

## Example queries

On the page:

- **Search**, Query **Reference dish** `Tuna Lover`, Find **Videos**: `download (15)` 0.7764, `download (12)` 0.7535, `download (14)` 0.7260. These are the same numbers the book's guide printed from `analyze_embeddings.py`.
- **Search**, Query **Video** `download (12)`, Find **Video frames**: the top 8 frames all come from `download (12)` itself: frames of one clip are closer to each other than to any other clip.
- **Check**, `Miso Chicken` against `download (15)` at 0.75: PASSED (0.7624), best frame at 4.8 s. Then look at **Every video against Miso Chicken** to see which other clips pass.
- **Explore**, Videos and dishes, K-Means k = 4: the dish photos form their own group (see [FAQ](#faq-and-caveats)). Switch to **Video frames**: each clip's frames sit together, and HDBSCAN finds them.
- **Debug** on, then any of the above: the **LanceDB query** expanders show the calls.

From Python:

```python
import lancedb

db = lancedb.connect("byteeats.lancedb")
media, frames = db.open_table("media"), db.open_table("frames")

tuna = media.search().where("media_id = 'Tuna_Lover'").select(["embedding"]).limit(1).to_list()[0]["embedding"]

# Which videos look most like the Tuna Lover dish? (exact scan of 39 rows)
(
    media.search(tuna)
    .distance_type("cosine")
    .where("media_type = 'video'", prefilter=True)
    .select(["media_id", "_distance"])
    .limit(3)
    .to_pandas()
)

# Quality check: the best frame of one video against the dish (BTree prefilter + vector index)
(
    frames.search(tuna)
    .distance_type("cosine")
    .where("video_id = 'download (15)'", prefilter=True)
    .select(["frame_index", "timestamp_s", "_distance"])
    .limit(1)
    .to_pandas()
)
```

Similarity is `1 - _distance`.

## Ported from the original

| | Original (FAISS) | This port (LanceDB) |
|---|---|---|
| Where embeddings live | One `.npy` file plus a JSON sidecar per video and image in `data/embeddings/` | The `embedding` column of `media` and `frames`, next to the files and metadata |
| Per-frame vectors | Computed, averaged, then discarded; the quality check decoded the video and re-ran ResNet on 8 frames for every check | Stored in `frames`; the quality check is a prefiltered vector search |
| Vector store | In-memory FAISS index, rebuilt at API startup | `byteeats.lancedb/` on disk (or LanceDB Cloud), built once by `scripts/` |
| Index types | `IndexFlatL2`, `IndexIVFFlat`, `IndexHNSWFlat`, picked per API start | Exact scan for `media`; IVF_HNSW_SQ on `frames`; `03_compare_indexes.py` measures the alternatives |
| Distance | Squared L2, score 1 / (1 + d) | Cosine, similarity 1 - d: the same numbers `analyze_embeddings.py` printed |
| Neighbours and clusters | API endpoint returning JSON; "clusters" were any pair closer than the 25th-percentile distance | Details dialog with ranked neighbours and a clickable map; UMAP + K-Means/HDBSCAN, named by nearest dish |
| Visualisation | Dash dashboard calling the FastAPI server: a PCA scatter and a quality form | One Streamlit page, reading LanceDB directly |
| Processes to run | API server, dashboard, quality CLI (three terminals) | `make data`, then `make run` |
| Embedding numbers | ResNet-18, every 5th frame, mean then normalise | Unchanged (batched; image-to-video similarities match the guide to 4 decimals) |

Where the book's guide steps went:

| Guide step | In this port |
|---|---|
| `run_pipeline.sh --generate-embeddings` | `make data` |
| `analyze_embeddings.py` (top videos per reference image) | Search tab: Query a reference dish, Find Videos |
| `test_similarity_search.py` (Flat, IVF, HNSW) | `make compare`, and the sidebar's exact/nprobes/refine controls |
| `run_pipeline.sh --start-api`, `test_api_client.py` | Not needed: the app and Python read LanceDB directly |
| `run_pipeline.sh --quality-check`, the quality API | Check tab |
| `run_pipeline.sh --start-dashboard` (PCA plot) | Explore tab and the details dialog |

The quality-check scores move slightly because the check now uses the 24 stored frames (every 5th) rather than 8 freshly decoded ones. The guide's four examples keep their verdicts:

| Video | Reference | Threshold | Guide (8 frames) | Port (24 frames) | Result |
|---|---|---|---|---|---|
| download (25) | Salmon_Edamame | 0.80 | 0.7753 | 0.7738 | FAILED |
| download (20) | Salmon_Edamame | 0.75 | 0.6371 | 0.6638 | FAILED |
| download (15) | Miso_Chicken | 0.75 | 0.7522 | 0.7624 | PASSED |
| download (9) | Miso_Salmon | 0.65 | 0.6640 | 0.6581 | PASSED |

`make compare` on the sample data (39 queries, top 10, 768 frames, 3 partitions; Apple-silicon laptop):

| Index | recall@10, nprobes = 2 | recall@10, nprobes = 1 |
|---|---|---|
| Flat (exact) | 1.000 | 1.000 |
| IVF_FLAT | 1.000 | 0.977 |
| IVF_SQ | 0.987 | 0.982 |
| IVF_HNSW_SQ | 0.987 | 0.967 |
| IVF_PQ | 0.841 | 0.851 |

All of them answer in about 2 ms here. At 768 rows the index choice is about recall rather than speed; the gap in latency opens up with millions of frames.

## FAQ and caveats

- **Why do the dish photos cluster apart from the videos?** ResNet-18 sees studio lighting, framing and the videos' on-screen overlays as part of the picture, so the photos sit closer to each other than to any clip: dish-to-dish similarities run 0.76 to 0.93, dish-to-video 0.51 to 0.80 (video-to-video 0.64 to 0.93, median 0.80). That's why the quality check compares a dish with a video's best frame, not with the video's mean vector.
- **ResNet-18 is an ImageNet classifier, not a food or text model.** The port keeps it so the numbers match the book. Swapping in CLIP would add text search ("a salmon bowl with edamame"); see [TODO.md](TODO.md).
- **The thresholds are the book's.** 0.75 means "about as close as the sample data gets"; they aren't calibrated against labelled data.
- **`03_compare_indexes.py` runs locally only.** It builds indexes on a scratch copy.
- **The cloud path is untested here.** `connect_db` and the chunked writes follow the fe-demos conventions, but nothing in this repo has been pushed to LanceDB Cloud yet.
